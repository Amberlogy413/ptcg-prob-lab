## 1. 為何需要一個獨立引擎

對戰沙盤 `src/state/battleStore.ts` 已經是一套**忠實的規則子集**(合法出牌、
攻擊、擊倒、獎賞、勝負、特殊狀態檢查),但它是一個 Zustand store —— 與 React
綁定、帶有副作用、用隨機 `uid()` 產生牌張、靠 UI 逐步驅動。它能讓**人**好好對戰,
卻無法讓**程式**以「狀態 → 合法動作 → 步進 → 獎勵」的方式高速、可重現地自我對弈。

強化學習需要的正是後者:一個 **headless(無介面)、純函數、可重現** 的環境。
這就是 `src/engine/`。

設計鐵則(與 `src/lib/prob/` 同等):

- **純函數**:`applyAction(state, action, ctx)` 永不變更輸入,只回傳新狀態。
- **可重現**:洗牌用同一個 `mulberry32` 種子流,牌張用確定性 id(`p1-0`、`p1-1`…)。
- **零猜度**(本專案最高原則):引擎只開放它能**精確結算**的動作;任何需要玩家抉擇
  (搜尋、選棄、指定目標、擲銀)的卡效,寧可**暫不納入動作空間**,也絕不假裝結算。
  無法精確的數值(例如「×」「+」變動傷害)只以印刷底值近似,並在 `COVERAGE` 與
  §5 明明白白標示為近似,絕不當作精確結果。
- **共享原語對齊**:引擎與沙盤共享同一套底層原語(洗牌 / 發牌 / 抽牌 / 洗手入庫),
  由 `engineParity.spec.ts` 比對鎖死,杜絕這些**共享機制**悄悄分叉。動作 reducer
  則各自實作:引擎在影響學習健全性處**刻意比沙盤嚴格**,差異逐項列於 §4(非靜默)。

## 2. 模組結構

| 檔案 | 職責 |
|---|---|
| `engine/types.ts` | 純資料型別:`GameState`、`Action`(離散動作空間)、`EngineCtx`。牌張/盤面型別由 store 以 `import type` 重用(執行期抹除),全專案只有一份盤面定義。 |
| `engine/ops.ts` | 低階純盤面操作:洗牌發牌(`setup`)、抽牌(`drawN`)、棄手牌、洗手入庫、傷害、擊倒、取獎賞。逐一對應 store 私有 helper。 |
| `engine/cards.ts` | 已建模卡效(`battleEffects` 的純函數版):僅限確定性、無抉擇的支援者(博士的研究 / 莉莉艾的決心 / 裁判)。附 `COVERAGE` 誠實覆蓋率帳本。 |
| `engine/game.ts` | 核心 reducer:`newGame`、`legalActions`、`applyAction`、終局/勝負/獎勵。重用 `battleAttack` 的攻擊純函數。 |
| `engine/env.ts` | Gym 式環境包裝 `BattleEnv`:`reset` / `step` / `legalActions` / `observation`,以及把觀察攤平成定長向量的 `encodeObservation`(供神經網絡)。 |
| `engine/index.ts` | 對外 API barrel。 |

## 3. 狀態與動作空間

### `GameState`
完整、可序列化:`seed`、`shuffleNonce`、`turn`、`current`、`firstPlayer`、四個
每回合旗標、`everInPlay`、雙方 `PlayerBoard`。給定 `(seed, shuffleNonce)` 完全確定。

### `Action`(離散)
`playToActive` / `playToBench` / `evolve` / `attachEnergy` / `attachTool` /
`playStadium` / `playSupporter` / `retreat` / `attack` / `promote` / `endTurn`。

`legalActions(state, ctx)` 列出**當前玩家**所有合法動作;`applyAction` 對非法動作
是 no-op(回傳原狀態)。智能體永遠只從 `legalActions` 取樣 —— 這是「合法走子遮罩」。

## 4. 與沙盤的嚴格差異(刻意收緊,為 RL 健全性)

沙盤對人類寬鬆(容許手動修正);引擎在影響學習健全性處**更嚴格**,並如實記錄:

1. **進化**:需符合印刷的前一階名稱(同語系牌組內可靠),且該寶可夢非本回合才入場;
   先手第 1 回合不可進化。
2. **撤退**:必須有足夠附著能量支付撤退費用,並**真的棄掉**該數量能量;每回合一次。
   (沙盤刻意保留「手動付費」affordance,屬已記錄的 store↔engine 差異。)
3. **道具(Tool)**:每隻寶可夢上限 1 個。
4. **攻擊即結束回合**:攻擊結算後自動轉到對手回合(符合真實規則)。
5. **強制遞補**:戰鬥場空而備戰區有寶可夢時,唯一合法動作是 `promote`。
6. **先落 Active 才可落備戰**:Active 空置時不提供 `playToBench`(真實佈場順序)。
7. **先手第 1 回合抽牌**:`newGame` 內為先手玩家完成回合 1 的強制抽牌(發牌 7 → 抽後 8);
   現行規則下先手照抽,只是不可攻擊 / 不可用支援者。沙盤的回合 1 抽牌則是手動按鈕。
8. **牌庫耗盡即負**:輪到某玩家而其牌庫為空、無法完成回合開始的強制抽牌 → 該玩家落敗
   (`deckedOut` → `gameResult` reason `"deckOut"`)。沙盤只出警告、不自動判定。
9. **睡眠 / 麻痺不可攻擊**:引擎正確禁止;沙盤不檢查(攻擊由人手判斷)。
10. **store 的每回合上限**(1 能量 / 1 場地)現已在 store method 內 guard,與引擎一致
    (UI 一直有 gate;此次令底層 method 本身亦符合真實規則)。

## 5. 誠實覆蓋率(`COVERAGE`)

引擎是**忠實子集**,不是完整遊戲。已如實列明的暫行簡化:

- 攻擊只結算「傷害 + 弱點/抵抗」;印刷的**攻擊附帶效果**(上狀態、抽牌、棄牌、
  回血、自傷)**尚未套用**。
- **變動/條件傷害**(「50+」「60×」)只以**印刷底值近似** —— 真實倍率/加成不在資料內,
  故此值**絕不當作精確**(見 `battleAttack.isVariableDamage`)。
- 特殊狀態:中毒/灼傷檢查傷害會套用,睡眠/麻痺的 Active 已正確**禁止攻擊**;
  睡眠/麻痺/混亂的**恢復擲銀**留給呼叫者。
- **混亂**的 Active 之攻擊目前**不擲銀**(不會失敗、不自傷 30)—— 擲銀未建模。
- 因檢查傷害(毒/燒)而達到 HP 的寶可夢**不自動擊倒**(與沙盤一致);狀態擊倒 +
  取獎賞屬後續階段。
- 攻擊擊倒對手 Active 後,下一玩家的回合開始強制抽牌**排序在強制遞補之前**
  (現時無可觀測影響;無已建模效果依賴此次序)。
- **場地**採用 per-side 槽(與沙盤一致);真實的「單一共享場地區 + 同名不可重置」規則未建模。
- 特殊/未知能量以萬用方式支付任一費用符號(其屬性絕不被捏造)。
- **已建模卡效**:3 張無抉擇抽牌支援者(博士的研究 / 莉莉艾的決心 / 裁判)+ 5 張
  **需抉擇的高用率卡**(見下「抉擇即動作」)。其餘道具/特性主動效果尚未建模。

### 抉擇即動作(AI 步驟①的關鍵機制)

真實 PTCG 大部分卡都**需要玩家抉擇**(搜尋、選目標),所以「無抉擇」卡效只是一小撮。
要真正推進步驟①,引擎把**抉擇本身變成動作空間的一部分** —— agent 直接揀。已落地**五張**
(靠**確切 catalog 效果文字**偵測 + 呼叫端按卡種類 gate,非估名;以 `COVERAGE.targeted` 為準):

* **老大的指令(Boss's Orders,gust 支援者,用率約 90%)**:`playGust{ iid, targetUid }`
  —— 對手每隻備戰寶可夢各成一個合法動作;選中者與對手戰鬥場互換(舊戰鬥場退備戰、
  特殊狀態清除),卡進**我方**棄牌區,佔該回合支援者額度、先手回合 1 禁用。
* **寶可夢交替(Switch,物品)**:`playSwitch{ iid, benchUid }` —— 自己每隻備戰各成一個
  合法動作;與自己戰鬥場互換(退場者特殊狀態清除、傷害保留),物品無能量費用、不佔回合限制。
* **搜尋類**(`search{ iid, foundIid }`,牌庫/棄牌每張合資格卡各成一個合法動作):
  **巢穴球**(牌庫→基礎→備戰,重洗)、**大師球**(牌庫→任何寶可夢→手牌,重洗)、
  **夜間擔架**(棄牌→寶可夢或基本能量→手牌,不洗)。牌庫搜尋會重洗,令抽牌 HUD 維持均勻。
* **能量轉移(Energy Switch,物品)**:`energySwitch{ iid, fromUid, energyIid, toUid }` —— 把
  自己某隻寶可夢身上一個**基本能量**移到自己另一隻寶可夢身上(來源每個不同屬性 × 每個其他
  在場寶可夢各成一個合法動作;同源同屬性的重複能量會去重)。屬於搬遷已附能量,**不佔**該回合
  由手牌附能量的額度;物品本身用完入棄牌。

> **這道「已建模 vs 未建模」的鴻溝,正是七步走的第①步本體** —— 也就是日本 RL 團隊
> 花最多人力逐張卡實作的「Implemented cards」。它佔整個工程約九成工作量;「抉擇即動作」
> 就是逐步把這道鴻溝填平的方法。

## 6. 環境介面(步驟②)與自我對弈骨架

```ts
import { BattleEnv } from "../engine";

const env = new BattleEnv(catalog);          // catalog 提供攻擊/屬性事實
env.reset({ p1: deckA, p2: deckB, seed: 7 });

while (!env.done) {
  const legal = env.legalActions();          // 合法走子遮罩
  const action = policy(env.observation(), legal); // ← 智能體在此決策
  const { reward, done } = env.step(action); // 推進一步;reward 屬剛行動方視角
}
const winner = env.winner();
```

- `observation(pov)` 是**單一視角**摘要(只含公開資訊:對手手牌只見**數量**,絕不見內容)。
- `encodeObservation` 把觀察攤平成定長 `number[]`(目前為各區計數 + 戰鬥場對位);
  牌張身分嵌入屬訓練管線的後續工作 —— 此投影較粗,但引擎本身精確。

## 7. 由此到「真‧神經網絡 AI」的七步

| 步 | 內容 | 在何處執行 |
|---|---|---|
| ① 完整規則引擎(環境) | 逐張卡效 → `state→legalActions→step→reward`。**最大樽頸(約九成工作)** | 離線 / 本引擎(現為忠實子集) |
| ② RL 介面 | 觀察編碼 + 動作空間 + 獎勵 —— **本引擎 `BattleEnv` 已備骨架** | 本引擎(TS) |
| ③ 神經網絡 agent | 策略 + 價值網絡(PyTorch) | 離線(Python + GPU) |
| ④ 自我對弈訓練 | PPO 或 AlphaZero(MCTS),數百萬局 | 離線(Python + GPU) |
| ⑤ 評估 + 迭代 | 新版打舊版 / 打啟發式 bot,量勝率 | 離線 |
| ⑥ 匯出權重 | ONNX / TensorFlow.js(數 MB) | 離線 |
| ⑦ 瀏覽器推論 | `onnxruntime-web` / `tf.js` 即時出招 | 本 app(會新增依賴,需擁有者拍板) |

### 重要事實(對齊本專案理念)
- 訓練(③–⑥)**必須離線**在 Python + GPU 完成;本零後端純客戶端 app **跑不了訓練**,
  只能做最後的**推論**。
- 瀏覽器推論會引入 `tf.js`/`onnxruntime-web`(數 MB),與「零依賴」理念相悖,
  屬擁有者決策項。
- 在 ① 未補齊完整卡效之前,訓練出的智能體**只反映子集環境**的策略 —— 這點必須對使用者誠實。
